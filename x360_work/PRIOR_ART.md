## Уроки xbox360-nx (самый близкий к нам и самый подробный)
**CPU / сборка**
- Регистры r14–r31 как локальные (`non_volatile_as_local`) убирают вызовы `__savegprlr_*`/`__restgprlr_*` — у них это было ~14 % главного потока. Ломается в функциях, разбитых на куски (переход в другой кусок с живыми регистрами) — нужна пометка `share_registers` + проверка «чтение до записи» (`lee_antes.py`). `non_argument_as_local` у них ломал `__savevmx` (r12), `skip_lr` — игра читала `ctx.lr` в 21 месте. **Для MGR проверять каждую опцию отдельно.**
- **Прямые вызовы**: GCC не инлайнит вызовы через weak-алиасы `sub_X`, поэтому вызовы переписывают на `__imp__sub_X` (79 612 из 83 077), кроме подхваченных хуками. Без этого LTO почти бесполезен.
- **LTO** (`-flto -fno-fat-lto-objects`, линковка `-flto=2 -flto-partition=balanced`), **PGO** на GCC под Horizon (ловушки: `-fno-profile-values` обязателен — `tpidr_el0` = 0 при `-mtp=soft`; `-fprofile-correction`; `--wrap=fopen` для путей .gcda на SD; периодический `__gcov_dump`), **порядок функций** в линкер-скрипте (ловушка: `KEEP(*(.crt0))` первым, `_start` должен быть по адресу 0).
- Вместе прямые вызовы + LTO + PGO + порядок: 30,3 → ~34 кадров/с.
- **Нативные замены горячих функций с «охраной»**: сначала выполняются обе версии и сравниваются, потом проверка выборочно. Ещё +1,4 кадра/с и −70 % кадров ≥60 мс. `memmove`/`strncpy` — нативные через `[rexcrt]`.
- С LTO/PGO всплывает скрытый UB (у них — strict aliasing в xxHash сломал ключи кэша текстур). Нужны проверки во время работы.

**Horizon**
- Под hbl вся память (~3,2 ГБ) — куча; `UsedMemorySize` бесполезен. Лимит `LimitableResource_Memory` на отображения: при исчерпании `0xCE01`, не «нет памяти».
- Виды физической памяти x360 (0xA0…, 0xC0…, 0xE0…) — отображать кусок в вид только при первом обращении (по исключению), кусками 4 МБ; иначе 472 МБ реальной памяти превращались в 1782 МБ отображений.
- В libnx один стек исключений на процесс → при параллельных page fault поток «просыпается» с чужими регистрами. Нужен пул стеков/дампов (у них 8 слотов).
- Только приоритет **0x3B** делится по времени; остальные кооперативные — занятый поток не отпускает ядро. Гостевые потоки — 0x3B. Голодание лечить понижением приоритета «захватчика».
- Предпочтительное ядро поток не закрепляет; жёсткая маска закрепляет, но рендер-поток на одном ядре проседал.
- `std::thread::detach()` может бросить исключение — пулы постоянных потоков.
- Busy-wait'ы в D3D-слое игры (ожидание кольца GPU, `Sleep(0)`-опрос) держали 2 аппаратных потока на 100 % — подменены хуками с реальным ожиданием.
- Частоты: приложение может само попросить у `apm` конфигурацию `0x92220008` (GPU 460,8 МГц в handheld, память 1331,2) — это не разгон. В handheld по умолчанию GPU 307,2 МГц.
- `__nx_nv_transfermem_size` (8 МБ по умолчанию) ограничивает число NvMap-хэндлов (~4000) → ошибка `0x235C`.

**Графика**
- Эмуляция GPU (Xenia) на Switch — 1–3 кадра/с (~80 мкс CPU на draw).
- Перехват D3D API (как в Unleashed) им **не подошёл**: текстуры приходят с готовым D3D-описанием внутри данных игры (без `CreateTexture`), `SetTexture` копирует fetch-константу прямо в устройство. Они оставили D3D игры и читают PM4-кольцо в отдельном потоке («ring thread»), хуки только для опознания шейдеров (вершинные шейдеры D3D патчит на лету) и для синхронизации (SCRATCH_REG / WAIT_REG_MEM). Позже часть состояния передавали маркером вместо ~14 пакетов.
- **Для MGR это важно**: у нас в WTA/WTB у каждой текстуры готовый 52-байтный `D3DBaseTexture` с fetch-константой (`tools/wtb.py`) — ровно ситуация NFS, значит перехват `CreateTexture` их не увидит. Решать перед M2.
- deko3d против NVK у них: тот же средний FPS, но нет 50-мс остановок на создание пайплайнов, ниже провалы, NRO на 37 % меньше.
- Шейдеры: XenosRecomp → HLSL → DXC SPIR-V (→ SPIRV-Cross → GLSL → uam → DKSH для deko3d); вершинные шейдеры опознаются хуками на создании, не по микрокоду.
- Мерить на **штатных частотах** с первого дня: разогнанные цифры скрыли, что упор в GPU.
